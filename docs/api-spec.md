## 1. API Overview

### 1.1 Base URLs

| Service | Development | Production |
|---------|-------------|------------|
| REST API (PostgREST via Kong) | `http://localhost:8000/rest/v1` | `https://dt.unr.uni-freiburg.de/db/rest/v1` |
| Auth (GoTrue) | `http://localhost:8000/auth/v1` | `https://dt.unr.uni-freiburg.de/db/auth/v1` |
| Storage | `http://localhost:8000/storage/v1` | `https://dt.unr.uni-freiburg.de/db/storage/v1` |
| Realtime | `http://localhost:8000/realtime/v1` | not proxied |
| Studio | `http://localhost:54323` | not exposed (SSH tunnel only, see [data-access-guide.md](data-access-guide.md)) |

Production is reachable on **port 443 only** (campus client-subnet ACL); there is no `:8000`
on the server. Production and development are schema-identical. The live endpoint list, with
columns, is the OpenAPI description at `GET /rest/v1/`, and the portal's developer guide at
<https://dt.unr.uni-freiburg.de/portal/api/>.

### 1.2 API Design Principles

The REST API is **fully auto-generated by PostgREST v13.0.7** from the PostgreSQL schema. There are no hand-written route handlers. Every resource endpoint is a view in the `public` schema, defined in `supabase/migrations/` (mirrored into `docker/volumes/db/init/`), over tables in the domain schemas (`shared`, `trees`, `sensor`, `pointclouds`, `environments`, `imagery`, `forest_floor`).

Key principles:
- Every public view is a readable endpoint; writable views are either simple (auto-updatable) views or carry `INSTEAD OF` triggers routing mutations to the underlying table
- Resources are addressed by lowercase view name (e.g., `trees`, `sensor_readings`, `point_clouds`)
- PostgREST filter operators control query narrowing without custom query parameters
- Row Level Security (RLS) on the domain tables decides what each role may write; the tables without RLS are listed in §2.2
- S3 URI paths are stored for LiDAR point cloud files (`.las`, `.laz`, `.ply`); file content is not served through this API

PostgREST also serves the domain schemas `shared`, `pointclouds`, `trees`, `sensor`,
`environments` and `imagery` (`PGRST_DB_SCHEMAS`), selected per request with an
`Accept-Profile: <schema>` header (reads) or `Content-Profile: <schema>` (writes). The same
RLS policies and grants apply there. The portal reads `shared.account_events` this way.

### 1.3 API Versioning

All REST endpoints are served at `/rest/v1`. There is currently no second API version. Kong routes `/rest/v1/*` to the PostgREST service internally.

## 2. Authentication & Authorization

### 2.1 Authentication Methods

Every request to `/rest/v1/*` requires two headers:

| Header | Value | Purpose |
|--------|-------|---------|
| `apikey` | `<ANON_KEY>` or `<SERVICE_ROLE_KEY>` | Kong consumer identification |
| `Authorization` | `Bearer <JWT>` | PostgREST role resolution via Supabase Auth JWT |

Both keys are defined in `docker/.env` as `ANON_KEY` and `SERVICE_ROLE_KEY`. For anonymous public access, the anon key is used for both headers (it is itself a valid JWT). A signed-in user sends the anon key as `apikey` and their own access token as `Authorization`.

**JWT Token Structure (HS256, issued by GoTrue v2.182.1):**

```json
{
  "header": { "alg": "HS256", "typ": "JWT" },
  "payload": {
    "role": "anon",
    "iss": "supabase",
    "iat": 1714000000,
    "exp": 1714086400
  }
}
```

For signed-in users, `role` is `authenticated`, `sub` contains the GoTrue user UUID, and
`app_metadata.role` carries the account's **role tier** (absent for a read-only account). A
tier change takes effect at the next sign-in or token refresh (`JWT_EXPIRY`, 3600 s).

### 2.2 Authorization (Role Tiers via RLS)

PostgREST maps the JWT `role` claim to a PostgreSQL role. Within `authenticated`, RLS policies
call `shared.is_contributor()`, `shared.is_curator()` and `shared.is_admin()`, which read
`app_metadata.role`. The tiers are cumulative: admin > curator > contributor > none.

| Caller | JWT | Access |
|--------|-----|--------|
| anonymous | `role: anon` | SELECT on every public view; may call `ue_sensor_state_at`, `ue_sensor_readings_latest`; `request_job` is refused |
| account, no tier | `role: authenticated` | Read-only: SELECT, its own rows in `job_status`, `list_accounts` refuses it |
| contributor | `app_metadata.role: contributor` | INSERT on field data; full CRUD on metadata; `request_job()` |
| curator | `app_metadata.role: curator` | Contributor rights, plus UPDATE/DELETE on field data, every job in `job_status`, `climate_pathways` / `management_regimes`, managing read-only and contributor accounts |
| admin | `app_metadata.role: admin` | Curator rights, plus granting `curator` and `admin` |
| `service_role` | `SERVICE_ROLE_KEY` | Bypasses RLS; the only caller of the five connector RPCs (§3.4) |

**Write rules by table group** (policies in `supabase/migrations/`, latest `20261029110000`,
`20261030100000` and `20261030120000`):

| Group | Tables | INSERT | UPDATE / DELETE |
|-------|--------|--------|-----------------|
| Field data | `trees`, `stems`, `point_clouds`, `environments`, `images`, `phenology_observations`, `deadwood`, `ground_vegetation`, `qsms`, `qsm_cylinders`, `tree_graph_edges`, `roots`, `crown_foliage_profiles`, `simulation_runs` | contributor | curator |
| Sensor readings | `sensor.sensor_readings` | contributor | nobody (service_role only) |
| Metadata | `species`, `plots`, `scenarios`, `campaigns`, `sensors`, `scanners`, `management_events`, `disturbance_events` (+ `disturbance_events_trees`), `processes`, `process_parameters*`, `process_metrics` | contributor | contributor |
| Locations | `shared.locations` | contributor | UPDATE contributor; no DELETE |
| Attribute provenance | `shared.attribute_provenance` | contributor | UPDATE contributor; DELETE curator |
| Scenario axes | `climate_pathways`, `management_regimes` | curator | curator |
| Lookups | `variant_types`, `sensor_types`, `soil_types`, `climate_zones`, `tree_status`, morphology lookups, `tree_part_types`, `root_system_types`, `scanner_types` | — | — |
| Jobs | `shared.processing_jobs` | only via `request_job()` | the job runner (direct database connection) |

**Tables without RLS**, guarded by grants alone: `shared.variants`, `trees.growth_simulations`,
`sensor.sensor_tree_links`, `trees.data_source_types`, `sensor.units`, `shared.lookup_registry`,
`shared.audit_log_phenology_observations`. `anon` and `authenticated` hold no write grant on
any of them, so they are written only by `service_role`, silva-connector (libpq) and the
import scripts.

#### Public view categories

The domain data lives in the custom schemas (`shared`, `trees`, `sensor`, …); `public` holds only views. PostgREST serves `public` as its **default profile**, so exposing views there lets clients use simple names (`/trees`) without a schema-selection header. The public views fall into three groups:

1. **Pass-through views** — 1:1 wrappers over a single domain table (`trees`, `sensors`, `sensor_readings`, `species`, all morphology/lookup tables, …). Writable ones are auto-updatable (`security_invoker = on`, so RLS applies to the caller) and/or carry `INSTEAD OF` triggers; since migration `20261030110000` the trigger-backed views (`trees`, `sensors`, `campaigns`) return zero rows when RLS skips an update instead of reporting success.
2. **Composite / export views** — `variants`, `growth_simulations` / `simulation_runs` (simulator output), `job_status`, and `attribute_provenance` (`security_invoker='on'`, read-only over REST — the only writer is `set_location_attributes`).
3. **Unreal Engine views** (`ue_*`). A NULL `scenario_name` in `ue_environments` means the row is not a projection -- an observed climatology or a permanent site property -- rather than a missing pathway. `ue_climate` is the same data **merged across `variant_name`**: one row per location, scenario and period with each measurement taken from whichever dataset supplied it. Since XRFF-395 two datasets fill different columns of the same window (CHELSA the temperature and precipitation, `ssp-co2` the CO2), so `ue_environments` returns two half-empty rows where a scenario picker wants one full one. Read `ue_climate` for a scene; read `ue_environments` when you need which dataset a single number came from.

> **`ue_trees`** is the single flat tree endpoint. It replaced the former `forest_state` view (XRFF-240). Filter by `variant_id` to load one time step: `GET /ue_trees?variant_id=eq.<id>`.

#### Linking trees ↔ sensors ↔ readings in Unreal Engine

The `ue_*` views form the complete chain UE needs; join on stable keys:

```
GET /ue_trees?variant_id=eq.<v>                              → tree catalogue (tree_id, tree_entity_id)
GET /ue_sensors?tree_entity_id=eq.<tree_entity_id>            → all sensors on that physical tree
GET /ue_sensor_readings?sensor_id=eq.<sensor_id>&order=timestamp.desc&limit=96   → that sensor's readings
GET /ue_climate?location_id=eq.<id>&scenario_name=eq.ssp370&order=start_year  → that site's climate pathway, one row per window
```

Join sensors to trees by **`tree_entity_id`** (the persistent physical-tree UUID), not `tree_id` (a single variant row) — this keeps the link stable across growth variants. `ue_sensors` also carries the latest reading inline (plus `sensor_model` = real instrument, `data_owner`, the generic `source` = provider e.g. `aquarius`, and `plot_name` = the sensor's monitoring sub-area), so a per-tree sensor list needs no extra readings or `/sensors` call. `tree_id`, `tree_entity_id` and `linked_tree_*` are populated by `scripts/import/link_sensors_to_trees.py` (see [database-schema.md §3.9](database-schema.md)); meteo/soil-station sensors have `NULL` tree fields. The twelve soil probes on one tree are told apart by the placement parsed from the label: `placement_ring` (`stem` | `middle` | `edge`, near → far), `placement_direction` (`N` | `E` | `S` | `W` | `NE`), `placement_depth_cm` and `placement_distance_cm`; `NULL` means the label says nothing (migration `20260924100000`).

`ue_trees` also carries `sensor_ref` and a `has_sensors` boolean, so UE can flag instrumented trees without a second query — filter with `GET /ue_trees?has_sensors=eq.true`.

### 3.2 Standard CRUD Methods

| Method | Path | Description | Auth Required |
|--------|------|-------------|---------------|
| GET | `/rest/v1/{resource}` | List / filter records | anon key |
| GET | `/rest/v1/{resource}?{filters}&select={cols}` | Projected and filtered list | anon key |
| POST | `/rest/v1/{resource}` | Create record | user JWT with the tier in §3.1 |
| PATCH | `/rest/v1/{resource}?{filters}` | Update matching records | user JWT with the tier in §3.1 |
| DELETE | `/rest/v1/{resource}?{filters}` | Delete matching records | user JWT with the tier in §3.1 |

An UPDATE or DELETE that RLS does not allow is not an error: it matches zero rows. Send
`Prefer: return=representation` and check for an empty array.

**Example: GET trees filtered by location**

Request:
```
GET /rest/v1/trees?location_id=eq.1&data_source_type_id=eq.1&select=variant_id,tree_entity_id,height_m,species_id&limit=50
apikey: <ANON_KEY>
Authorization: Bearer <ANON_JWT>
```

`data_source_type_id` references `/rest/v1/data_source_types` (1 `field`, 2 `lidar`, 3 `photogrammetry`, 4 `estimated`, 5 `simulated`).

Response (200 OK):
```json
[
  {
    "variant_id": 2,
    "tree_entity_id": "31e059c6-77b5-4502-bccd-65799b46ce75",
    "height_m": 27.24,
    "species_id": 1
  }
]
```

**Example: POST new tree variant** (contributor or above)

Request (POST `/rest/v1/trees`):
```json
{
  "location_id": 1,
  "variant_type_id": 1,
  "species_id": 1,
  "measurement_date": "2025-09-11",
  "data_source_type_id": 1,
  "height_m": 22.4,
  "position": "SRID=4326;POINT(7.85 47.99)"
}
```

Response (201 Created with `Prefer: return=representation`):
```json
[{ "tree_id": 101, "tree_entity_id": "b2c3d4e5-...", "height_m": 22.4, ... }]
```

### 3.3 Sensor Readings (Time-Series Queries)

| Pattern | Query String | Description |
|---------|-------------|-------------|
| Latest N readings | `?sensor_id=eq.{id}&order=timestamp.desc&limit=100` | Most recent readings |
| Time range | `?sensor_id=eq.{id}&timestamp=gte.{iso8601}&timestamp=lte.{iso8601}` | Bounded time window |
| Quality filter | `?sensor_id=eq.{id}&quality=eq.good&order=timestamp.desc` | Good-quality only |
| Active sensors | `?is_active=eq.true&location_id=eq.{id}` | Active sensors at a location (on `/sensors`) |

| `ue_sensor_readings_latest` | `(p_limit int = 100000, p_location_id int = NULL)` → `SETOF ue_sensor_readings` | everyone, including anon |
| `list_accounts` | `()` → `TABLE(email, role, created_at, last_sign_in_at, must_change_password, manageable)` | authenticated; refuses callers below curator |
| `create_account` | `(p_email text, p_role text = NULL)` → `TABLE(email, role, password)` | authenticated; curator (read-only or contributor) or admin (any tier) |
| `set_account_role` | `(p_email text, p_role text = NULL)` → `TABLE(email, role)` | authenticated; curator (between read-only and contributor) or admin (any tier); never your own |
| `reset_account_password` | `(p_email text)` → `TABLE(email, password)` | authenticated; curator (read-only and contributor accounts) or admin (any); never your own |

The four account RPCs are SECURITY DEFINER and check the caller's tier themselves; each call is
logged to `shared.account_events`. `create_account` and `reset_account_password` return a
one-time password and flag the account `must_change_password`. The portal's account page
(<https://dt.unr.uni-freiburg.de/portal/account/>) is their front end — see
[data-access-guide.md](data-access-guide.md#user-management).

The first five are the **complete write surface for connectors**. `aquarius-connector` and `open-data-connector` reach the database only through them, with the service-role key — no direct SQL, no database credentials. Since migration `20261030120000` they are executable by `service_role` only (`anon` and signed-in accounts get 401/403). One RPC per landing zone, chosen by the shape of the datum: time series into the sensor tables, static site attributes onto `shared.locations`, period aggregates and scenarios into `environments.environments`.

| Function | Source File | Description |
|----------|-------------|-------------|
| `bulk_upsert_sensors` | `10-baseline-schema.sql` | Upsert sensors from JSON array (conflict on `external_id`) |
| `bulk_insert_readings` | `10-baseline-schema.sql` | Bulk insert readings, skip duplicates (unique on `sensor_id`+`timestamp`) |
| `set_location_attributes` | `23-open-data-landing-zones.sql` | Set site attributes on one `shared.locations` row and record where each came from, atomically |

| `refresh_soil_aggregates` | `33-soil-aggregates-from-sensors.sql` | Derive `avg_soil_moisture_percent` and `avg_soil_temperature_c` per location and year from the twin's own sensor readings and write them to `environments.environments` |

**RPC: set_location_attributes**

Writes the values and their provenance rows in one transaction, so a value and its stated source can never disagree. `p_process_id` is required and must already exist in `shared.processes` — that row carries the source's version, licence and citation, which matters because this database is published.

`p_attributes` accepts exactly these eight columns and **raises on any other key** rather than skipping it: `elevation_m`, `slope_deg`, `aspect`, `soil_type_id`, `climate_zone_id`, `forest_growth_region`, `soil_moistness`, `soil_nutrient_supply`. Identity, geometry and audit columns are not reachable through this path. A rejected call writes nothing.

Idempotent: re-running leaves one `shared.attribute_provenance` row per column, updated in place.

Request body (process 23 is the `eu-dtm` acquisition row):
```json
{
  "p_location_id": 2,
  "p_attributes": { "elevation_m": 1183.4, "slope_deg": 12.5, "aspect": "NE" },
  "p_process_id": 23,
  "p_source_uri": "<URL the values were read from>",
  "p_license": "CC-BY-4.0"
}
```

Response (200 OK) — the number of columns written:
```json
[{ "out_written_count": 3 }]
```

**RPC: upsert_environment**

One row per (location, scenario, variant type, variant name, period), keyed by the unique index `uq_environments_natural_key`. Use a deterministic `p_variant_name` — it is part of the key, so a changed name inserts a new row rather than updating the existing one.

**Merges, does not replace.** A measurement key absent from `p_values` leaves the stored value alone, so two sources can populate different columns of the same period row. The consequence: this RPC cannot set a value back to `NULL` — delete the row to reset one.

`p_values` accepts the 14 measurement columns of `environments.environments` (`avg_temperature_c` … `stress_factor`) and raises on any other key. `p_process_id` is required, as above.

Request body (process 27 is the `chelsa` acquisition row, variant type 7 `model_output`, scenario 7 `ssp370` at ecosense):
```json
{
  "p_location_id": 1,
  "p_variant_type_id": 7,
  "p_variant_name": "chelsa",
  "p_process_id": 27,
  "p_scenario_id": 7,
  "p_values": { "avg_temperature_c": 12.11 },
  "p_start_date": "2041-01-01T00:00:00Z",
  "p_end_date": "2070-12-31T00:00:00Z",
  "p_description": "CHELSA V2.1 SSP3-7.0 30-year mean"
}
```

Response (200 OK) — `out_inserted` is `false` when an existing row was refreshed:
```json
[{ "out_environment_id": 17, "out_inserted": false }]
```

**RPC: refresh_soil_aggregates**

The one writer of `environments.environments` that acquires nothing: it reads the twin's own soil sensors and writes the result back, under `variant_name = 'twin-sensors'` and `variant_type_id = 6` (`sensor_derived`). No scenario — this is what was measured, not a projection.

The value is a **quarter-balanced nested mean**: equal weight per sensor within a day, per day within a quarter, and per quarter within the year. The readings arrive in month-long windows whose volumes differ by up to a factor of ten, so a flat mean over all readings is weighted by sampling density rather than by time — 10.75 °C against the balanced 10.59 at ecosense for 2025.

It **refuses rather than guesses**, per quantity, and says so in the returned `out_status`:

* a quantity without four quarters of at least `p_min_days_per_quarter` measured days is skipped, because an annual mean over three quarters is a seasonal mean wearing a year's label;
* a quantity whose sensors disagree on the unit is skipped, because 129 soil-moisture sensors declare `m3_m3` where 507 declare `percent`;
* readings outside the range `sensor.sensor_types` declares for the quantity are excluded before any of this.

Sensor depth is not recorded in the twin (`installation_height_m` is NULL on all 1,280 soil sensors), so the value is a mean across the depths the network sits at, not a profile. The row's `description` says so.

Request body — every parameter optional; the defaults refresh every location and year:
```json
{
  "p_location_id": 1,
  "p_year": 2025,
  "p_min_days_per_quarter": 7,
  "p_dry_run": false
}
```

Response (200 OK) — one row per location-year considered, **including the ones it refused**, so a caller that only counted successes would still see a site drop out of coverage:
```json
[{
  "out_location_id": 1,
  "out_year": 2025,
  "out_start_date": "2025-01-15",
  "out_end_date": "2025-11-14",
  "out_avg_soil_moisture_percent": 22.160,
  "out_avg_soil_temperature_c": 10.585,
  "out_environment_id": 72,
  "out_status": "written: soil moisture and soil temperature"
}]
```

Idempotent: a second run refreshes the same row.

Provenance written by `set_location_attributes` is readable at `GET /rest/v1/attribute_provenance`, with the source's name, version and citation resolved from `shared.processes`.

**RPC: ue_sensor_state_at**

Latest reading per sensor at or before `p_timestamp`, within `p_lookback` (default: 4 × the
sensor's `sampling_interval_seconds`). Sensors with no reading in the window are absent rather
than filled with a stale value. `source` names the provider (`aquarius`, or a model such as
`open-meteo`); filter on it before presenting a value as an observation.

```
POST /rest/v1/rpc/ue_sensor_state_at
{"p_timestamp": "2025-07-15T12:00:00Z"}
```

**RPC: ue_sensor_readings_latest**

The newest `p_limit` rows of `ue_sensor_readings`, optionally of one site, sorted by
`sensor_id` then `timestamp_unix`. Filter by site with `p_location_id`, not with a PostgREST
filter (that applies after the limit).

```
GET /rest/v1/rpc/ue_sensor_readings_latest?p_limit=100000&p_location_id=1
```

## 4. Request & Response Formats

### 4.1 PostgREST Query Parameters

| Parameter | Syntax | Description | Example |
|-----------|--------|-------------|---------|
| `select` | `col1,col2,col3` | Column projection | `?select=variant_id,height_m,species_id` |
| `order` | `col.asc` or `col.desc` | Sort order | `?order=timestamp.desc` |
| `limit` | integer | Max rows returned | `?limit=100` |
| `offset` | integer | Skip rows (for pagination) | `?offset=200` |

### 4.2 PostgREST Filter Operators

Filters are applied as query parameters in the form `?{column}={operator}.{value}`:

| Operator | Meaning | Example |
|----------|---------|---------|
| `eq` | Equal | `?sensor_id=eq.5` |
| `neq` | Not equal | `?quality=neq.bad` |
| `lt` | Less than | `?height_m=lt.10` |
| `gt` | Greater than | `?height_m=gt.30` |
| `gte` | Greater than or equal | `?timestamp=gte.2025-01-01T00:00:00Z` |
| `lte` | Less than or equal | `?timestamp=lte.2025-12-31T23:59:59Z` |
| `like` | Pattern match (case-sensitive) | `?variant_name=like.silva_*` |
| `ilike` | Pattern match (case-insensitive) | `?scientific_name=ilike.*fagus*` |
| `in` | Match any value in list | `?location_id=in.(1,2)` |
| `is` | IS NULL / IS TRUE / IS FALSE | `?decommission_date=is.null` |

### 4.3 Standard Response Structure

PostgREST returns plain JSON arrays. No envelope wrapper is added.

**Success (list):**
```json
[
  { "variant_id": 1, "height_m": 28.5, "species_id": 3 },
  { "variant_id": 2, "height_m": 31.2, "species_id": 3 }
]
```

**Pagination header (returned when `Prefer: count=exact` is sent):**
```
Content-Range: 0-49/1200
```

## 5. Error Codes

### 5.1 HTTP Status Codes

| Status | Meaning | When Used |
|--------|---------|-----------|
| 200 | OK | Successful GET, PATCH, RPC |
| 201 | Created | Successful POST with `Prefer: return=representation` |
| 204 | No Content | Successful POST/PATCH/DELETE without representation |
| 400 | Bad Request | Malformed filter, invalid column name, type mismatch, RPC parameter rejected |
| 401 | Unauthorized | Missing or invalid `apikey` / `Authorization` header; `anon` without the privilege |
| 403 | Forbidden | Signed-in role without the privilege, or an RLS `WITH CHECK` failure on insert |
| 404 | Not Found | Resource (view) does not exist in `public` schema |
| 406 | Not Acceptable | Invalid `Accept` header |
| 409 | Conflict | Unique constraint violation (e.g., duplicate `sensor_id`+`timestamp`) |
| 500 | Internal Server Error | Database error or unhandled constraint violation |

### 5.2 PostgREST Error Response Format

```json
{
  "code": "PGRST116",
  "details": null,
  "hint": null,
  "message": "The result contains 0 rows"
}
```

Common error codes:

| Code | Description |
|------|-------------|
| `PGRST116` | Query returned 0 rows when exactly 1 expected (`Prefer: single`) |
| `PGRST204` | Column does not exist in the view |
| `42703` | Unknown column in a filter |
| `42501` | Permission or RLS policy denied the operation; also `request_job()` without the contributor tier |
| `23505` | Unique constraint violation |
| `23503` | Foreign key constraint violation |
| `23514` | Check constraint violation |

## 7. Pagination

PostgREST uses `limit`/`offset` parameters. Total count is available via `Prefer: count=exact`.

**Request:**
```
GET /rest/v1/sensor_readings?sensor_id=eq.5&order=timestamp.desc&limit=100&offset=0
Prefer: count=exact
```

**Response headers:**
```
Content-Range: 0-99/45231
```

Without `Prefer: count=exact`, the total count is omitted for performance. For high-volume tables like `sensor_readings`, avoid `count=exact` in production queries.
