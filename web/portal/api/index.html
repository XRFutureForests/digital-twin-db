Developer guide

Every table of the twin is an HTTP endpoint (PostgREST behind Kong, Supabase-compatible). Reads need only the public key below; writes need a signed-in account with the right role — the database enforces the same rules as on the data page. How the data is organised: Docs.

Public (anon) key

Sent as the apikey header on every request. It identifies this deployment, not a person, and only grants what anonymous visitors may do anyway — safe to ship in a client.

Accountfrom the curator of your team; change the password on the account page

Port 443 only — other ports are blocked by the campus network, so ignore :8000 URLs in older docs. The service-role key is never handed out.

Sign in

A password sign-in returns an access_token (a JWT, valid one hour) and a refresh_token. Send the token as Authorization: Bearer … next to the apikey header. Without one you are anonymous: you can read, not write.

Three traps

    
    
      
  • A refused update is not an error. An update or delete your role may not make
        returns 200 with zero rows. Send Prefer: return=representation and check
        the response is not empty.
    • 
      
  • Corrections to measured data need a curator. Every change to heights, DBH,
        health and status is logged with who made it, and can be reverted.
    • 
      
  • This is the production twin. The VR client and dashboards read the same rows.
        Mark test rows (e.g. field_notes: "test"), or develop against a local copy of the
        stack — digital-twin-db,
        start with its RUNBOOK.md.

Run a model

    
Models run on the server: your app requests a job with one call, a runner picks it up within
      about a minute, and the results land back in the database. Requesting needs
      contributor. The job page does the same by hand.

    
1. Request

    
rpc/request_job returns a job id. The optional external_job_id is any
      string you choose; sending the same one again returns the first job instead of queueing a second,
      so a retrying app cannot start duplicates. Invalid parameters are refused at once with a readable
      message (HTTP 400).

    

    
2. Watch

    
Poll job_status until status is completed or
      failed. You see your own jobs; output_data holds the end of the tool's
      log, which is where a failure is explained.

    

    

      
statusmeaning

      
        
pendingqueued, no runner has taken it yet

        
runningthe tool is running

        
completedfinished; results written (or reported, for a dry run)

        
failedsee error_message and output_data

      
    

    
3. Read the result (SILVA)

    
    
      
  • dry_run: true writes nothing; output_data.stdout reports per period how many trees grew and died, mean DBH and height.
    • 
      
  • no_promote: true writes the per-tree trajectory to growth_simulations (one row per tree and 5-year step) and a row in simulation_runs, without creating forest states. Find your run in simulation_runs, then filter growth_simulations by its simulation_run_id. Use this mode for an app.
    • 
      
  • With neither flag the run also becomes forest states (silva_2030, …) that the VR client lets people walk through. Agree that with the lab first, and never send replace: true without asking: it deletes the existing chain of that name.
    •

Ground rules

    
    
      
  • One model run at a time. The server runs one job at once and has little memory to spare during a large run — do not queue requests in a loop; use external_job_id so retries do not duplicate.
    • 
      
  • Read in pages with limit/offset, and always filter sensor_readings by sensor and time.
    • 
      
  • Secrets stay out of repositories. The anon key may ship in a client; your password and tokens may not.
    • 
      
  • Schema changes go through the lab. Code against the public endpoints; they stay stable when base tables change.
    • 
      
  • Questions, a role change, a correction to measured data: the curator of your team.
